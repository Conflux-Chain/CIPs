## Simple Summary

When a Core Space contract calls an eSpace address through the CrossSpaceCall internal contract, an EIP-7702 delegation on the callee is not resolved: the delegation designator bytes are executed as the callee's code instead of the delegated contract's code. This CIP makes cross-space calls resolve EIP-7702 delegations the same way in-space eSpace calls do, from an activation height.

## Abstract

[CIP-7702](./cip-7702.md) introduced EIP-7702 delegation to eSpace: an EOA's code may be a delegation designator (`0xef0100 || address`), and a message call targeting such an account executes the code of the delegated address in the context of the authority account. The in-space call path implements this resolution, but the cross-space call path of the CrossSpaceCall internal contract ([CIP-90](./cip-90.md)) loads the callee's raw code without resolving the designator. Since `0xef` is not a valid opcode, calling a delegated eSpace account from Core Space executes the designator bytes and fails immediately, instead of executing the delegated code. This CIP aligns the cross-space call path with the in-space behavior.

## Motivation

EIP-7702 delegated accounts (e.g. smart-wallet EOAs) are expected to behave like the delegated contract for any message call targeting them. A Core Space contract calling such an account via `callEVM`, `staticCallEVM`, or `transferEVM` currently hits the raw designator bytes, so the call — including a plain value transfer through `transferEVM`, since the designator makes the account's code non-empty — fails on the invalid `0xef` opcode. This breaks cross-space composability for any eSpace account using EIP-7702.

## Specification

From the activation height, when the CrossSpaceCall internal contract constructs the eSpace call frame for `callEVM(bytes20,bytes)`, `staticCallEVM(bytes20,bytes)`, or `transferEVM(bytes20)`, and the eSpace callee's code is an EIP-7702 delegation designator (`0xef0100 || address`), the code and code hash of the call frame are loaded from the delegated address instead of the callee, identically to an in-space message call to the same account. The frame still executes in the context of the callee (the authority account): address, balance, and storage are those of the callee.

All other aspects of the cross-space call are unchanged, including gas charging, the mapped-account nonce increment, and the `Call`/`Outcome` event logs.

Blocks below the activation height keep the current behavior.

## Rationale

### Following in-space semantics

EIP-7702 specifies that delegation is resolved for any code execution targeting the authority account. The cross-space call is a message call into eSpace, so it follows the same rule; the previous behavior was an implementation oversight, not a design decision.

### No additional gas charge

EIP-2929-style accounting (as adopted by [CIP-645](./cip-645.md)) prices delegation resolution as one extra account access on the in-space call path. The cross-space call already charges a fixed overhead that includes a full transaction base cost (21000 gas) on top of the call cost, which covers the single extra account load by a wide margin, so no additional charge is introduced and the internal contract's gas accounting is left untouched.

## Backwards Compatibility

This CIP is Spec Breaking. Contracts relying on cross-space calls to delegated accounts failing on the invalid designator bytes would observe different results after activation; such reliance is not considered meaningful usage.

## Security Considerations

The change only substitutes the code loaded for the eSpace call frame; value flow, context address, and gas accounting are unchanged. The delegated code already runs for in-space calls to the same account, so no new code-execution surface is introduced. The extra account read per cross-space call is bounded (delegation resolution does not recurse) and is covered by the existing fixed gas overhead, so it introduces no DoS vector.
